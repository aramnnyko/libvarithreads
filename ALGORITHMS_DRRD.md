# DRRD — Deficit Round Robin with Dynamic Weights

## 1. Назначение и место в проекте

DRRD — планировщик легковесных потоков пользовательского уровня,
первый из планировщиков `libvarithreads`. Реализуется в двух видах:

- **симулятор** (`sim/`) — для верификации алгоритма и сбора статистики;
- **рантайм** (`src/sched/drrd.c`) — когда появится ядро потоков.

Документ описывает алгоритм в терминах, общих для обеих реализаций,
но единственный источник истины — текущий код `sim/`.

## 2. Постановка задачи

Планировщик управляет множеством потоков с приоритетами. Потоки
одинакового приоритета образуют группу. Число групп `G ≤ 10`,
фиксировано при инициализации (`sim_init` принимает массив приоритетов).

**Требования:**

- Пропорциональное распределение планировочных решений: за полный
  цикл каждая группа получает ровно `W_base_g = priority(g) × count(g)`
  вызовов. Гарантия на уровне потока — §5.
- Динамическое добавление и удаление потоков без остановки планировщика.
- Блокировки: недополученные кванты не теряются, компенсируются при
  разблокировке.
- Сложность операций — `O(G)`, при `G ≤ 10` практически `O(1)`.

## 3. Структуры данных

**Поток** (`mock_thread_t`):
- `id` — уникальный идентификатор (монотонно растёт);
- `priority` — приоритет;
- `state` — `THREAD_READY` / `THREAD_BLOCKED` / `THREAD_ZOMBIE`;
- `debt` — недополученные кванты из-за блокировок;
- `next`, `prev` — соседи в круговом двусвязном списке группы;
- `stat` — запись статистики;
- `user_data` — для генератора (контролируется только генератором);
- `got_debugging` — отладочное.

**Группа** (`mock_group_t`):
- `priority` — приоритет всех потоков группы;
- `count` — число живых потоков;
- `W` — текущий вес группы; **пересчитывается** в `recalculation_deficit`
  как `priority × count − fant_calls` (для активных групп);
- `W_base` — базовый вес `priority × count`; меняется инкрементально
  на `±priority` при add/remove;
- `deficit` — DRR-дефицит;
- `fant_calls` — «фантомные вызовы»: сумма кредитов `got` при создании
  минус `got` при удалении плюс число шагов, на которых группа была
  выбрана;
- `current` — указатель на текущий поток в круговом двусвязном списке
  (отдельного `head` нет).

**Глобальное состояние** (`sim_state_t`):
- `W` — текущая длина цикла; меняется на `±delta` при add/remove,
  сбрасывается на `W_base` при `reset`;
- `W_eff` — **DRR-квант**: величина, вычитаемая из `deficit` в каждом
  шаге; устанавливается в `reset` и `recalculation_deficit` значением
  `W − R`; между recalculations **постоянна**;
- `W_base` — `Σ priority_g × count_g` по живым потокам;
- `R` — число выполненных решений в текущем цикле;
- `thread_id`, `cycle` — служебные.

## 4. Двухслойная структура (концептуальная)

Код физически не разделён, но логически распадается на два слоя,
которые полезно различать при анализе. `sim_step` — координатор,
он обновляет состояние **обоих** слоёв за один вызов.

**Слой 1 — глобальный цикл.** Состояние: `W`, `W_base`, `R`.
Отвечает на вопрос «сколько всего решений надо выдать в этом цикле»
и «сколько уже выдано». Не знает о DRR, о группах, о `deficit`.

**Слой 2 — DRR.** Состояние: `W_eff`, `{deficit_g, W_g, current_g, fant_calls_g, count_g}`.
Отвечает на вопрос «как распределить фиксированный бюджет `W_eff` между
группами пропорционально `W_g`». Не знает о динамике и о `W`.

**Стык — `recalculation_deficit`.** Перезапускает DRR на оставшемся
бюджете:
```
W_eff := W − R                (см. теорему ниже)
deficit_g := W_g              (для всех активных групп)
```
С точки зрения слоя 2 это выглядит как `reset` цикла длины `W_eff`.
С точки зрения слоя 1 ничего не произошло: `W` и `R` продолжают
накапливаться.

**Теорема.** В момент каждого `recalculation_deficit` выполняется
`W_eff = W − R`. Доказательство. С момента последнего `reset` пусть
произошло `k` add и `m` remove. Тогда
```
W − W(0)        = Σ_adds delta − Σ_removes delta
W_base − W_base(0) = Σ_adds p − Σ_removes p
Σ fc            = R + Σ_adds got − Σ_removes got
```
(последнее — потому что `sim_step` увеличивает `fc` выбранной группы
и `R` на 1, взаимно сокращаясь; add/remove меняют `fc` на `±got`).
При отсутствии клампинга `got + delta = p` для каждой операции, откуда
`Σ got_add − Σ got_rem = W_base − W`. Значит
```
Σ fc = R + W_base − W
W_eff = Σ_active W_g = W_base − Σ fc = W − R.    ∎
```
Пустые группы в сумму не входят (их `fc = 0`, показано в §8), поэтому
`Σ_active W_g = W_base − Σ fc`.

**Ключевое следствие.** Если в момент `t` произошёл `recalculation`
и `R(t) = R₀`, то `W_eff = W − R₀`. Далее между recalculations `W_eff`
постоянна, каждый шаг `sim_step` увеличивает `R`. Через ровно `W_eff`
шагов `R` достигнет `W`, цикл закроется. Между recalculations
`W − R` **убывает**, а `W_eff` — нет; равенство `W − R = W_eff`
сохраняется только в точке recalc.

## 5. Инварианты

Для любого потока `t`, прожившего `N` полных циклов и не блокировавшегося:

```
Actual(t) = priority(t) × N
```

Точное равенство. Подтверждено стресс-тестами (100 сидов × 20k циклов,
до 1M потоков; у всех потоков `Diff = 0`). Теоретическое обоснование —
теорема §4 (в момент перезапуска DRR получает ровно оставшийся бюджет,
поэтому целочисленное округление не накапливается).

Общий инвариант учёта (проверяется `print_stats`):

```
Actual(t) + Debt(t) + FantTotal(t) + LostTotal(t) = Expected(t)
```

где `Expected(t) = priority(t) × общее_число_циклов`, `Debt(t) = debt_final(t)`
фиксируется в момент удаления потока (см. §8).

**Инварианты в моменты recalc** (`reset` или `recalculation_deficit`):

1. `W_eff = W − R` (теорема §4).
2. `deficit_g = W_g` для всех активных групп.
3. `W_g = priority_g × count_g − fant_calls_g`.

**Инварианты между recalculations** (в ходе `sim_step`):

4. `W_eff` постоянна, `W` постоянна (без add/remove), `R` растёт.
5. `Σ_active deficit_g = W_eff` (сохраняется: `update_deficit` добавляет
   `Σ W_g = W_eff`, `sim_step` вычитает `W_eff` у одной группы).
6. `R ≤ W`.

**Инвариант длины цикла** `R ≤ W`: 
- add увеличивает `W` (расслабляет), `R` не меняет — тривиально;
- remove уменьшает `W` на `delta`. По определению `delta = W_g − W_g'`,
  где `W_g' ≥ 0`. Значит `delta ≤ W_g`. А `W_g ≤ W_eff = W − R`
  (в момент предыдущего recalc `W_eff = Σ W_g`, а между recalc `W_g`
  не меняется). Следовательно, после remove `W' = W − delta ≥ W − W_eff = R`.

**Границы:**
```
W_base = Σ_{live g} priority_g × count_g
W      = W_base + Σ_g Δ_g,   Δ_g = W_g − W_base_g
```
Для активных групп после recalc `Δ_g = −fant_calls_g ≤ 0`; для пустых
`Δ_g = 0` (по определению: `W_base_g = 0`, `W_g = 0`, т.к. `fc = 0`).
`Δ_g` **не сходятся к нулю постепенно** — они пересчитываются в момент
add/remove и обнуляются скачком при `reset`.

## 6. Базовый цикл

**Сброс** (`reset`, вызывается `sim_run` перед каждым циклом):

1. `W := W_eff := W_base`; `R := 0`.
2. Для каждой **активной** группы: `W := W_base`, `fc := 0`, `deficit := 0`.
   Пустые группы пропускаются.
3. `update_deficit()`: `deficit_g += W_g` для активных. Итог: `deficit_g = W_g`.
4. `stat_reset()` — сброс поцикловых счётчиков статистики.

**Шаг** (`sim_step`):

1. Если `W == 0` — выход (нет активных групп; цикл уже закрыт).
2. `g := sim_select_group()` — активная группа с максимальным `deficit`.
   При равенстве — **наименьший индекс** (код использует `>`, а не `>=`).
   Если `W > 0`, то хотя бы одна активная группа есть, и `g ≠ −1`.
3. `r := handle_thread_state(g->current)`:
   - **BLOCKED** → `thread->debt++`, `stat_thread_blocked`, вернуть `CONTINUE`;
   - **READY** → `stat_thread_ready`; если `thread->debt > 0`, то
     `thread->debt--`, `stat_thread_repay` (второй квант погашения
     в этом же шаге); вернуть `CONTINUE`;
   - **ZOMBIE** → `handle_thread_remove(g->current)` (см. §8); вернуть `ABORT`.
4. Если `ABORT` — **выход без изменений слоя 1** (R, W не трогаются;
   `calls`, `fant_calls`, `deficit` не трогаются; указатель `current`
   уже обновлён внутри удаления).
5. Иначе (фиксация решения):
   - `g->fant_calls++`;
   - `g->deficit -= W_eff`;
   - `sim.R++`;
   - `g->current = g->current->next`.
6. `update_deficit()`: `deficit_j += W_j` для каждой активной группы.
7. Цикл продолжается внешним `while (R < W)`. При `R == W` цикл закрыт,
   следующий `reset` запускает новый.

**Почему вычитается `W_eff`, а не `W`.** `W_eff` — бюджет текущего
прогона DRR (равен `W − R` в момент recalc). В устоявшемся режиме
`W_eff == W`. После динамики `W_eff < W`, и вычитание `W` переполнило
бы дефициты.

**Долг.** Блокировка не отменяет решение: группа уже «заплатила»
(`fc`, `R` увеличены, `deficit` уменьшен). Поток фиксирует недополученный
квант в `debt`. При разблокировке он получает дополнительный квант
**без** увеличения `fc` и `R` — группа уже «заплатила» за него ранее.
Суммарное число учтённых решений не нарушается.

## 7. Динамика: добавление потока (`sim_create_thread`)

Поток приоритета `p` добавляется в группу `g` в середине цикла.

**Требование:** приоритет `p` должен быть **предварительно зарегистрирован**
в `sim_init` (`find_group` возвращает `−1` для неизвестного приоритета,
и `&sim.groups[-1]` — UB). Приоритет `p > 0` (иначе `W_base_g = 0`
и поток никогда не будет выбран).

### Что вычисляет `compute_share(g)`

Функция возвращает пару `(got, delta)` для **позиции `current`**:

- `got` — сколько квантов `current` уже получил к данному моменту цикла
  (при нулевом `current` — «гипотетический» кредит, соответствующий
  позиции группы в глобальном цикле);
- `delta` — сколько ему осталось получить до конца цикла.

Семантика: `got + delta = priority` (без клампинга). Новый поток
встаёт «на место `current`» позиционно и по учёту.

### Код `compute_share` (по коду `drrd.c`)

**Группа пуста (`count == 0`):**
```
R == 0      : got = 0,           delta = p
R >= W      : got = p,           delta = 0
иначе       : delta = floor(p × (W − R) / W)
              got   = p − delta
```
Здесь `delta` округляется **вниз**, `got = p − delta` — вверх.
Смысл: `delta` — доля `p`, пропорциональная оставшейся части цикла;
`got` — всё остальное. Первая ветвь — цикл ещё не начался; вторая —
цикл уже закрыт (или `W = 0`).

**Группа непуста:**
```
got   = floor(g->fant_calls / g->count)
delta = max(0, p − got)         (клампинг)
```
Здесь `got` округляется **вниз** (это нижняя граница числа вызовов
`current`), `delta = p − got` — вверх.

**Округление — не одно и то же в двух случаях.** Для пустой группы
вниз идёт `delta`, для непустой — `got`. Формулы дают кредит **одного
смысла** (позиция `current`), но не гарантируют совпадения в 1:1.
В устоявшемся режиме они отличаются не более чем на 1.

**Зачем именно такой `got`.** Он сохраняет инвариант среднего:
```
floor((fant_calls + got) / (count + 1)) = floor(fant_calls / count)
```
(все деления — целочисленные). Без этого среднее по группе сдвинулось
бы при каждом добавлении, и следующая динамическая операция считалась
бы неправильно. `got` как кредит — **условие корректности учёта**,
а не оценка «заслуг» нового потока.

**Клампинг `delta = max(0, p − got)`.** Срабатывает, если `got > p`.
Под инвариантом `fant_calls ≤ p × count` (`got = floor(fc/count) ≤ p`)
клампинг недостижим. Инвариант подтверждён эмпирически (фаззер до 1M
потоков), формальное доказательство — открытый вопрос (§11). Клампинг —
**safety net**: если он всё же сработает, `got + delta ≠ p` и точность
§5 нарушится. См. §11.3.

### Вставка и корректировки

Новый поток помещается в круговой двусвязный список сразу после
`g->current`; если группа пуста — становится единственным элементом
и `current`. Позиция задаёт только порядок обхода, не долю.

- Слой 1: `sim.W += delta`, `sim.W_base += p`.
- Слой 2: `g->W_base += p`, `g->fant_calls += got`, `g->count++`.
- Стык: `recalculation_deficit()` — перезапуск DRR на оставшейся
  части (§4).

**Консервативность округления.** `delta` (непустая) округляется вверх,
`got` — вниз; для пустой — `delta` вниз, `got` вверх. В обоих случаях
новый поток получает чуть меньше идеальной доли, остальные группы —
чуть больше. Это выбор в пользу уже присутствующих потоков.

## 8. Динамика: удаление потока

Удаление в два этапа.

**Пометка** (`sim_remove_thread`): `thread->state := THREAD_ZOMBIE`.
Поток остаётся в списке, но не выполняет работы.

**Физическое удаление** (`handle_thread_remove`, из `sim_step` при
встрече зомби):

1. `(got, delta) := compute_share(g)` — для позиции `current`. Так как
   поток сам стал `current`, его «получено» и «осталось» совпадают
   с `got` / `delta`.
2. Слой 1: `sim.W -= delta`, `sim.W_base -= p`.
3. Слой 2: `g->W_base -= p`, `g->fant_calls -= got`, `g->count--`.
4. Удаление из кругового списка. Если `current` указывал на удаляемый
   узел — сдвиг на `next`; если список стал пуст — `current := NULL`.
5. `recalculation_deficit()` — перезапуск DRR на оставшейся части.
6. `stat_thread_remove(t, delta)` — фиксирует `missed_after = delta`,
   `debt_final = t->debt`, `removed_at = sim.cycle`. Затем `free(t)`.

**Почему ZOMBIE не потребляет квант.** Планировщик уже выделил группе
текущее решение. Если бы мы удалили зомби и продолжили без
корректировки, группа потеряла бы квант, за который уже «заплатила».
Вместо этого `fant_calls` и `R` не увеличиваются, `W` уменьшается на
`delta`, `recalculation_deficit` перезапускает слой 2 на новой
оставшейся части: решение «возвращается» планировщику и
перераспределяется.

**Почему отложенное удаление.** Если удалять поток сразу, он может быть
не `current`, и пришлось бы немедленно корректировать историю — а для
этого нужно точное число выполнений. Зомби позволяет дождаться момента,
когда поток станет `current`: тогда `got = floor(fant_calls/count)` —
та же формула, что и при добавлении. Это даёт `O(1)` памяти на поток.

**Долг удалённого потока.** С точки зрения **планировщика** долг
аннулируется: поток удалён, кванты не будут погашены. С точки зрения
**статистики** долг фиксируется в `debt_final` и входит в `SumCheck`
отдельным слагаемым. Поэтому инвариант §5 сходится: `Actual + Debt +
FantTotal + LostTotal = Expected`, где `LostTotal = delta` (только
`missed_after`, без долга), а `Debt = debt_final` — отдельное поле.

**Симметрия с добавлением — процедурная, не числовая.** `delta_add` и
`delta_rem` — **разные и не связанные** величины: `delta_add`
определяется позицией `current` в момент добавления, `delta_rem` —
позицией удаляемого потока, когда он сам стал `current`. Симметрия в
наборе шагов: в обоих случаях вычисляется пара `(got, delta)` и
одинаково корректируются `sim.W`, `sim.W_base`, `g->W_base`,
`g->fant_calls`, `g->count` с последующим `recalculation_deficit`.
Именно процедурное единообразие обеспечивает корректность инвариантов
§5.

**Пустая группа после удаления имеет `fc = 0`.** При удалении последнего
потока `got = floor(fc/1) = fc`, значит `fc` после операции `= fc − fc = 0`.
Это используется в теореме §4 (`Σ_active fc = Σ fc`).

## 9. Долг и блокировки

- Поток в `BLOCKED` не выполняется, но группа уже получила это
  решение (`fc`, `R` увеличены, `deficit` уменьшен).
- Поток фиксирует квант в `debt`.
- Когда поток становится `READY` и подходит его очередь, он выполняет
  штатный квант, затем — при `debt > 0` — **один** дополнительный квант
  погашения (`debt--`), без увеличения `fc` и `R`.

**Почему долг гасится сразу.** Группа уже учла квант в своей квоте;
повторное проведение не нарушает баланс между группами. Погашение при
первой возможности гарантирует, что долг не «уходит в никуда».

**Почему вставка после `current`.** `current` — следующий на выполнение;
его позиция — точка отсчёта. Новый поток получает ту же долю, что и он,
и встаёт рядом. Альтернатива «перед `current`» дала бы те же доли, но
отложила бы первый квант нового потока почти на полный обход — хуже
по латентности без выигрыша в справедливости.

## 10. Сложность

Все операции (выбор группы, add, remove) — `O(G)`, `G ≤ 10`,
практически `O(1)`. Внутригрупповые манипуляции со списком — `O(1)`.

**Пропорциональность:** за полный цикл группа `g` получает ровно
`W_base_g = priority_g × count_g` решений. Каждый поток получает ровно
`priority` квантов. Точность — 100% (§5), подтверждено стресс-тестами
до 1M потоков.

## 11. Открытые вопросы

1. **Debt cap — сознательный trade-off, не баг.** Верхняя граница на
   `debt` не задана. Без ограничения долг растёт линейно при долгой
   блокировке и погашается по одному кванту за решение. При долге,
   сопоставимом с длиной цикла, поток-должник после разблокировки
   получает двойные кванты много решений подряд — фактически
   монополизирует процессор на время погашения. Варианты:
   - **без границы** (текущий выбор): точность §5 сохраняется полностью,
     но возможна длительная монополизация после долгой блокировки;
   - `MAX_DEBT` с отбрасыванием лишнего: нарушает точность, ограничивает
     окно погашения;
   - `MAX_DEBT` с переносом: лишнее помечается как «фоновый долг» с
     низким приоритетом погашения.

   Точность и отсутствие монополизации **несовместимы** в этой модели;
   выбор — на уровне требований рантайма.

2. **Блокировка в середине кванта.** В симуляторе квант атомарен:
   поток либо получает его целиком, либо не получает. В рантайме
   возникнет вопрос: если поток блокируется по собственному вызову
   посреди кванта, считается ли квант доставленным частично?
   Отложено до реализации рантайма.

3. **Клампинг `delta = max(0, p − got)`.** Под инвариантом
   `fant_calls ≤ priority × count` недостижим; в фаззере не срабатывает.
   Инвариант подтверждён эмпирически, но формальное доказательство
   отсутствует. Если клампинг сработает, точность §5 нарушится, т.к.
   теорема §4 предполагает `got + delta = p`. Требуется либо
   формальное доказательство инварианта, либо явная гарантия того,
   что клампинг — мёртвый код (можно удалить).

4. **Внешние ограничения, не проверяемые кодом:**
   - `find_group` возвращает `−1` для незарегистрированного приоритета;
     `sim_create_thread` требует предварительной регистрации в `sim_init`;
   - `priority > 0` обязателен (`priority = 0` → `W_base_g = 0` → поток
     никогда не выбран);
   - переполнение `W`, `W_eff`, `fant_calls`, `deficit` при экстремальных
     нагрузках: счётчики 64-битные, при 1M потоков и 20k циклов запаса
     достаточно, но это не проверено на предельных сценариях.

## 12. Приложение: поля статистики (`print_*`)

**Таблица потоков** (`print_thread_stats`):

- **ID**, **Prio** — идентификатор и приоритет.
- **CreatedAt** — номер цикла создания; `0` — до симуляции.
- **RemovedAt** — номер цикла удаления; `−1` — жив до конца.
- **FrstRunAt**, **LastRunAt** — циклы первого/последнего фактического
  выполнения; `−1` — ни разу.
- **AliveFull** — число полностью прожитых циклов (`actual_cycle`;
  циклы создания/удаления не учитываются).
- **Expected** — `priority × cycles_lived`.
- **FantTotal** — `missed_before = got` на момент создания.
- **LostTotal** — `missed_after = delta` на момент удаления.
- **Debt** — `debt_final` на момент удаления или конца симуляции.
- **Actual** — реальное число выполнений.
- **SumCheck** — `Actual + FantTotal + LostTotal + Debt`.
- **Diff** — `Expected − SumCheck`. **Идеал — ноль для всех потоков**
  (не «±1»).

**Сводка по группам** (`print_group_stats`): суммы по потокам группы
(`TotalExp`, `TotalAct`, `Fant`, `Lost`, `Debt`, `SumCheck`, `Diff`).

**Сводка по долгам** (`print_stats_dept`): суммарные и пиковые
`debt_accrued`, `debt_repaid`, `debt_final`, `debt_max` по всем
потокам, а также идентификаторы потоков-рекордсменов. Проверяется
`Σ debt_accrued = Σ debt_repaid + Σ debt_final` (в коде —
`total_accrued == total_repaid + total_lost`, где `total_lost`
суммирует `debt_final`; это **не** `missed_after`).

**Гистограмма** (`print_diff_histogram`): распределение
`|Expected − SumCheck|` по потокам. Идеал — все потоки в столбце `0`.
