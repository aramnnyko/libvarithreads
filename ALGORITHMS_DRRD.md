# DRRD — Deficit Round Robin with Dynamic Weights

## 1. Назначение и место в проекте

DRRD — планировщик легковесных потоков пользовательского уровня,
первый из планировщиков `libvarithreads`. Реализуется в двух видах:

- **симулятор** (`sim/`) — для верификации алгоритма и сбора статистики;
- **рантайм** (`src/sched/drrd.c`) — когда появится ядро потоков.

Документ описывает алгоритм в терминах, общих для обеих реализаций.

## 2. Постановка задачи

Планировщик управляет множеством потоков с приоритетами. Потоки
одинакового приоритета образуют группу (класс эквивалентности).
Число групп ограничено сверху: `G ≤ 10`.

**Требования:**

- Пропорциональное распределение планировочных решений: за полный
  цикл каждая группа получает число вызовов, равное сумме приоритетов
  её потоков. Гарантия формулируется на уровне потока (см. §4).
- Динамическое добавление и удаление потоков без остановки планировщика
  и без полной перестройки очередей.
- Обработка блокировок: недополученные кванты не теряются, а
  компенсируются при разблокировке.
- Сложность всех операций — `O(G)`, при `G ≤ 10` практически `O(1)`.

## 3. Структуры данных

**Поток** (`mock_thread_t`):
- `priority` — приоритет потока;
- `state` — `READY` / `BLOCKED` / `ZOMBIE` / `DONE`;
- `debt` — недополученные кванты из-за блокировок;
- `next` — следующий поток в круговом списке группы.

**Группа** (`mock_group_t`):
- `priority` — приоритет потоков группы (одинаков для всех);
- `count` — число живых потоков, включая зомби до физического удаления;
- `W` — текущий вес группы в цикле (может временно отличаться
  от `W_base` при динамике);
- `W_base` — базовый вес, `priority × count`;
- `deficit` — дефицит DRR;
- `calls` — число планировочных решений, выделенных группе в цикле;
- `fant_calls` — «фантомные» вызовы, используются для оценки среднего
  числа вызовов на поток (`fant_calls / count`);
- `head`, `current` — указатели в круговом списке.

**Глобальное состояние** (`sim_state_t`):
- `W` — текущая длина цикла;
- `W_base` — базовая длина цикла, `Σ W_base(g)`;
- `R` — число выполненных решений в текущем цикле.

## 4. Инварианты

Для любого потока `t`, прожившего `N` полных циклов и не блокировавшегося:

```
Actual(t) = priority(t) × N
```

Точное равенство, без «в среднем». Погрешность ±1 квант возникает
только при создании или удалении самого потока в середине цикла
(см. §6, §7) и не накапливается между циклами.

Общий инвариант учёта, проверяемый статистикой:

```
Actual(t) + Debt(t) + FantTotal(t) + LostTotal(t) = Expected(t) ± 1
```

где `Expected(t) = priority(t) × общее_число_циклов`.

Инвариант дефицитов после каждой динамической операции:

```
deficit_j = W_j × R − W × calls_j    для всех групп j
```

Инвариант весов:

```
W_base = Σ_g (priority(g) × count(g))
W      = W_base + Σ_g Δ_g
Δ_g    = W_g − W_base_g
```

где `Δ_g` — временные отклонения веса группы от базового, возникающие
при добавлении и удалении потоков. `Δ_g` **могут быть отрицательными**:
для потока, добавленного в пустую группу, отклонение равно `−got`,
то есть меньше нуля. `Δ_g` **не сходятся к нулю постепенно** —
они сокращаются в момент удаления потока и обнуляются скачком
при `reset` в начале следующего цикла. `Δ_g` для пустой группы
сохраняется как резидуальный вес до `reset` и не влияет на
активные группы.

Инвариант длины цикла:

```
R ≤ W
```

Сохраняется при динамике, потому что `Δ_g` при добавлении вычисляется
**только от недополученной части** потока — доли в оставшейся части
цикла. Добавляемый поток не может запросить больше, чем осталось
решений; удаляемый не может «отобрать» у цикла больше, чем ему было
обещано.

## 5. Базовый цикл планирования

Планирование идёт циклами. Один цикл — полный формальный обход.

**Сброс** (`reset`):
- глобально: `W = W_base`, `R = 0`;
- для каждой группы: `g->W = g->W_base`, `g->calls = 0`,
  `g->fant_calls = 0`, `g->deficit = 0`.

**Шаг** (`sim_step`):

1. Обновление дефицитов: для каждой непустой группы `g->deficit += g->W`.
2. Выбор группы: группа с наибольшим `deficit`. Если активных групп
   нет — шаг завершается.
3. Выбор потока: `thread = g->current`.
4. Обработка состояния:
   - **BLOCKED** — поток не выполняется, `thread->debt++`.
   - **READY** — поток выполняет один квант. Если `thread->debt > 0`,
     немедленно выполняется ещё один квант погашения, `thread->debt--`.
   - **ZOMBIE** — вызывается `sim_mark_thread_removed_physical`,
     после чего шаг завершается. При этом:
     - **не** выполняются стандартные действия шага 5:
       `calls`, `fant_calls`, `R`, `deficit` не меняются;
     - указатель `current` **обновляется внутри процедуры удаления**,
       если он указывал на удаляемый узел (см. §7).
5. Фиксация решения (если поток не был ZOMBIE):
   - `g->current = thread->next`;
   - `g->calls++`, `g->fant_calls++`;
   - `g->deficit -= sim.W`;
   - `sim.R++`.
6. Цикл продолжается, пока `R < W`. При `R == W` цикл закрывается,
   начинается новый цикл с полным сбросом.

**Долг.** Когда поток заблокирован, группа уже получила это решение
(`calls`, `fant_calls`, `R` увеличены, `deficit` уменьшен). Поток
запоминает недополученный квант. При разблокировке он получает
дополнительный квант **без** увеличения `calls` и `R` — группа уже
«заплатила» за него ранее. Суммарное число учтённых решений не
нарушается.

## 6. Динамика: добавление потока (`sim_create_thread`)

Поток с приоритетом `p` добавляется в группу `g` в середине цикла.

**Точка отсчёта — `current`.** `current` — поток, который будет
выполнен следующим. Он всегда находится на нижней границе обхода:
к моменту, когда он стал `current`, он прошёл ровно
`floor(fant_calls / count)` раз, тогда как остальные потоки группы
прошли либо столько же, либо на один больше. Поэтому `current` —
единственная надёжная точка отсчёта для динамических операций.

**Вычисление доли нового потока.**

Если группа пуста (`g->count == 0`):
```
delta = (sim.W > 0) ? p * (sim.W - sim.R) / sim.W : p
got   = p - delta
```

Иначе:
```
got   = g->fant_calls / g->count    (целочисленное деление вниз)
delta = (g->priority > got) ? (g->priority - got) : 0
```

Здесь `got` — это **не** среднее по группе и **не** измерение
реальных выполнений нового потока. Это **кредит**, равный числу
выполнений `current`. Поскольку `current` всегда на нижней границе,
а `floor(fant_calls / count)` — это и есть нижняя граница,
формулы для непустой и пустой группы дают для нового потока ровно
тот же кредит, какой имеет `current`. Поток встаёт в обход
«на место `current`» не только позиционно, но и по учёту.

**Зачем именно кредит.** `got` определён требованием сохранить
инвариант среднего:

```
(fant_calls + got) / (count + 1) = fant_calls / count
```

Без этого среднее по группе сдвинулось бы при каждом добавлении,
и следующая динамическая операция считалась бы неправильно. `got`
как кредит — это условие корректности учёта, а не оценка
«заслуг» нового потока.

**Вставка в список.** Новый поток помещается в круговой список
сразу после `g->current`. Позиция вставки определяет только порядок
обхода, а не долю потока: доля `delta` вычислена заранее от
недополученной части цикла. Поэтому вставка после `current`
не даёт новому потоку никакого преимущества по числу квантов —
только определяет, где в обходе он появится.

**Корректировка весов:**
- `g->W += delta`, `sim.W += delta` — временные;
- `g->W_base += p`, `sim.W_base += p` — базовые.

**Корректировка счётчиков:**
- `g->fant_calls += got`;
- `g->count++`.

**Пересчёт дефицитов** всех групп:
```
g_j->deficit = g_j->W * sim.R - sim.W * g_j->calls
```

**Почему для пустой группы используется процентная формула.**
У пустой группы нет истории: `fant_calls = 0`, `count = 0`. Взять
`delta = priority` значило бы дать новому потоку полную долю на весь
цикл, даже если цикл почти завершён. Формула `delta = p × (W − R) / W`
выделяет долю строго пропорционально оставшимся решениям, а
`got = p − delta` даёт корректный кредит, симметричный формуле
непустой группы.

**Округление.** `delta = floor(p × (W − R) / W)`, `got = p − delta`.
То есть `delta` округляется вниз, `got` — вверх. Новый поток получает
чуть меньше своей идеальной доли, остальные группы — чуть больше.
Это консервативный выбор в пользу уже присутствующих потоков.

**Клампинг.** Формула `delta = max(0, p − got)` для непустой группы
срабатывает, если `fant_calls / count > p` (например, из-за
накопленного фантома от нескольких добавлений в одну группу).
В этом случае `delta = 0`, и появление потока не меняет `W`.

## 7. Динамика: удаление потока

Удаление в два этапа: пометка зомби и физическое удаление при
обнаружении планировщиком.

**Пометка** (`sim_mark_thread_removed`):
`thread->state = THREAD_ZOMBIE`. Поток остаётся в списке,
но не выполняет полезной работы.

**Физическое удаление** (`sim_mark_thread_removed_physical`,
вызывается из `sim_step` при встрече зомби):

1. Историческая доля удаляемого потока (здесь `p = g->priority`):
   ```
   got   = g->fant_calls / g->count
   delta = (g->priority > got) ? (g->priority - got) : 0
   ```
2. Корректировка весов:
   - `g->W -= delta`, `sim.W -= delta`;
   - `g->W_base -= p`, `sim.W_base -= p`.
3. Корректировка счётчиков:
   - `g->fant_calls -= got`;
   - `g->count--`.
4. Удаление из кругового списка с сохранением целостности.
   Если `g->current` указывал на удаляемый узел, `g->current`
   сдвигается на `thread->next`. Если `g->head` указывал на
   удаляемый узел, `g->head` сдвигается соответственно.
5. Пересчёт дефицитов всех групп.
6. Накопленный долг удалённого потока аннулируется.

**Почему ZOMBIE не потребляет квант.** Планировщик уже выделил группе
текущее решение. Если бы мы удалили зомби и продолжили без
корректировки `calls` и `R`, группа потеряла бы квант, за который
уже «заплатила». Вместо этого `calls`, `R` не увеличиваются,
а дефициты пересчитываются с новыми весами: решение «возвращается»
планировщику и перераспределяется в оставшейся части цикла.

**Почему отложенное удаление.** Если удалять поток сразу, он может
быть не `current`, и пришлось бы немедленно корректировать историю,
что требует знания точного числа его выполнений. Зомби позволяет
отложить удаление до момента, когда поток станет `current`:
тогда `got` вычисляется по среднему `fant_calls / count`. Это даёт
минимальную погрешность без счётчика выполнений на каждый поток.

**Симметрия с добавлением.** Поскольку `got` сохраняет
`fant_calls / count`, при добавлении и последующем удалении потока
`delta_add = delta_rem`. То есть «взял взаймы у цикла» и «вернул
циклу» — одно и то же число. Это и есть причина, по которой `W`
возвращается к `W_base` при опустошении группы.

## 8. Долг и блокировки

- Поток в состоянии `BLOCKED` не выполняется, но группа уже получила
  это решение (`calls`, `fant_calls`, `R` увеличены, `deficit` уменьшен).
- Поток фиксирует недополученный квант в `debt`.
- Когда поток становится `READY` и подходит его очередь, он выполняет
  штатный квант, затем — при `debt > 0` — дополнительный квант
  погашения, без увеличения `calls` и `R`.

**Почему долг гасится сразу, а не откладывается на следующий цикл.**
Гарантируется погашение при первой возможности. Группа уже учла этот
квант в своей квоте, поэтому повторное проведение не нарушает баланс
между группами.

**Почему вставка после `current`.** `current` — следующий на
выполнение; его позиция — точка отсчёта. Новый поток получает
такую же долю, как и он, и встаёт рядом с ним. Альтернатива —
вставить перед `current` — дала бы тот же результат по долям,
но отложила бы первый квант нового потока на почти полный
обход. После `current` — короче путь до первого кванта, без
изменения справедливости.

## 9. Сложность

Все операции (выбор потока, добавление, удаление) — `O(G)`, где `G` —
число групп. Поскольку `G ≤ 10` архитектурно, практически `O(1)`.

Внутригрупповые манипуляции со списком константны.

Пропорциональность: за полный цикл группа получает ровно `W_base`
решений. Каждый поток получает ровно `priority` квантов (см. §4);
погрешность ±1 возникает только при создании или удалении самого
потока в середине цикла и не накапливается.

## 10. Открытые вопросы

1. **Debt cap.** Верхняя граница на `debt` не задана. Без ограничения
   долг растёт линейно при долгой блокировке и погашается по одному
   кванту за решение. Если долг сопоставим с длиной цикла, поток-должник
   после разблокировки получает двойные кванты много решений подряд,
   что фактически монополизирует процессор на время погашения.
   Варианты:
   - без границы: строгая гарантия сохраняется полностью, но возможна
     длительная монополизация после долгой блокировки;
   - `MAX_DEBT` с ограничением: при превышении лишнее отбрасывается
     (нарушает строгую гарантию, но ограничивает окно погашения);
   - `MAX_DEBT` с сохранением: лишнее переносится, но помечается
     как «фоновый долг» с низким приоритетом погашения.
   Решение — после прогонов симулятора с длительными блокировками.

2. **Блокировка в середине кванта.** В симуляторе квант атомарен:
   поток либо получает его целиком, либо не получает. В рантайме
   возникнет вопрос: если поток блокируется по собственному вызову
   посреди кванта, считается ли квант доставленным частично?
   Отложено до реализации рантайма.

3. **Гарантия при динамике.** Утверждение §4 («`Actual = priority × N`
   точно») требует симуляторной проверки в сценарии «соседи
   добавляются и удаляются, поток `T` не трогают и не блокируют».
   Согласованность формул `delta` и `got` при добавлении в пустую
   и непустую группу — необходимое условие для этой гарантии;
   проверка должна подтвердить, что этого условия достаточно.

## 11. Приложение: поля статистики симуляции

**Таблица потоков** (`sim_print_stats`, `sim_print_stats_diff_only`):

- **ID** — уникальный идентификатор потока.
- **Prio** — приоритет потока.
- **CreatedAt** — номер цикла создания; `1` — до начала симуляции.
- **RemovedAt** — номер цикла удаления; `-1` — жив до конца.
- **AliveFull** — число полностью прожитых циклов.
- **Expected** — `priority × общее_число_циклов`.
- **FantTotal** — недополучено из-за позднего создания.
- **LostTotal** — недополучено из-за раннего удаления; включает
  аннулированный долг.
- **Debt** — текущий накопленный долг.
- **Actual** — реальное число выполнений.
- **SumCheck** — `Actual + FantTotal + LostTotal + Debt`.
- **Diff** — `Expected - SumCheck` (только в `_diff_only`).

**Сводка по группам** (`sim_print_group_stats`):

- **Grp**, **Prio** — индекс и приоритет группы.
- **TotalExpected**, **TotalActual** — суммы по потокам группы.
- **Fant**, **Lost**, **Debt** — суммы соответствующих полей.
- **IdealMax** — `priority × сумма прожитых циклов`.
- **Efficiency** — `TotalActual / IdealMax`.
- **BlkLost** — чистые потери из-за блокировок.
- **BlkForgiv** — число успешных погашений долга.

**Гистограмма ошибок** (`sim_print_diff_histogram`): распределение
`|Expected - SumCheck|` по потокам. Идеал — все потоки в столбце `0`.
